NF525 — Plan de Conformité Technique Précis
Ce qui est codé, ce qui manque, la procédure d'attestation
Implémenté
  • Inaltérabilité (I) — SHA-256 chaîné. Chaque seal contient le hash du précédent. FiscalEngine.sealEntry()
  • Sécurisation (S) — HMAC-SHA256 avec clé par tenant. Test non-forgeabilité. CryptoService.signFiscalData()
  • Fiscal genesis seal — GENESIS_ROOT dès la création du tenant. TenantSeeder.seed()
  • Fast path node:crypto — Évite jsdom lenteur sur rush 1000tx. CryptoService.generateHash()
  • Mode training — TRAINING_MODE_UNSIGNED_HASH pour démo. isTrainingMode flag
  • Stress test 1000 tx — BlackFriday.test.ts, CertificationRunner.test.ts. tests/benchmarks/
  • FEC export — Export comptable mensuel. api/admin/finance/fec/export/
  • SovereignLedger QA — runInquisiteurQA() : scan binaire total, LOCKDOWN si corruption. SovereignLedger.ts
Manquant
  • Clôtures journalières (J) — Z_REPORT auto à la clôture de caisse. sealPeriod() est un stub minimal
  • Clôtures mensuelles (M) — Totalisation mensuelle signée. FinanceCore.ZReport existe mais non déclenché
  • Clôtures annuelles (A) — Grand total perpétuel NF525 ISCA. Non implémenté
  • Archivage signé 10 ans — Conservation obligatoire. LegalArchiveService = alias FiscalEngine
  • Attestation éditeur rédigée — Document légal à auto-déclarer. Non existant
  • Rapport de contrôle interne — Audit ISCA documenté. Non existant

Sécurité — Vulnérabilités Identifiées
Issues concrètes dans le code, triées par sévérité
🔴
PIN 0000 par défaut CRITIQUE
TenantSeeder seed l'admin avec adminPin: '0000'. Si l'email de bienvenue ne force pas le changement immédiat, le compte est ouvert. → Générer un PIN aléatoire + l'envoyer dans l'email de bienvenue.
🔴
FISCAL_SIGNING_SECRET absent = crash en prod CRITIQUE
FiscalKeyService.requireKey() throw 'FISCAL_SIGNING_KEY_MISSING' sans clé. En prod sans cette var, chaque vente POS crash. Doit être dans les env vars Vercel avant le premier déploiement.
🟡
Rate limiter non persistant MOYEN
ipRateLimiter = new Map() dans signup/route.ts. Remis à zéro à chaque redéploiement ou en mode serverless avec plusieurs instances. En prod : utiliser Upstash Redis ou Vercel KV.
🟡
ROOT_ADMIN_PIN sans valeur par défaut = bonne pratique BIEN
Le code throw si ROOT_ADMIN_PIN n'est pas configuré. Pas de fallback. C'est volontaire et correct.
🟡
Sentry commenté = zéro monitoring erreurs prod MOYEN
// import Sentry from "@sentry/nextjs"; dans NexusFiscalProvider.tsx. En production, les erreurs 500 silencieuses sont invisibles. Activer Sentry avant le premier client.
🟡
NEXUS_TENANT_SECRET non documenté MOYEN
Présent dans .env.example : "Secret HMAC pour les writes signés SovereignGuard". À vérifier que SovereignGuard valide réellement cette signature en production.
🔵
MonkeyChaosAgent protégé par ORACLE_CHAOS_KEY BIEN
Le ChaosAgent ne s'active que si la clé env correspond. Aucun risque de déclenchement accidentel.

function parseCSVLine(line: string, sep = ','): string[] {
  const result: string[] = [];
  let cur = '', inQuotes = false;
  for (const ch of line) {
    if (ch === '"') { inQuotes = !inQuotes; continue; }
    if (ch === sep && !inQuotes) { result.push(cur.trim()); cur = ''; }
    else cur += ch;
  }
  result.push(cur.trim());
  return result;
}

🧠 Philosophie

Le NexusEventBus transforme l'OS en système neuro-réactif : les composants ne s'appellent plus directement, ils émettent des événements versionnés (v: 1) et s'abonnent à des réactions. Trois niveaux de priorité : CRITICAL (séquentiel, bloquant — fiscal, souveraineté), HIGH (parallel allSettled — stock, RH, compliance) et BACKGROUND (microtask — IA, CRM, météo). Règle d'or : tout événement lié à une transaction fiscale ou à un stock utilise emitDurable(), jamais un emit() nu. Un crash entre le Nexus.adapter.set() et le emit() ne peut plus faire disparaître de données.

🔒 P0 — Fondations Résilience
✓
EventOutbox — emitDurable()
Chaque événement critique est d'abord persisté dans la table IndexedDB busOutbox (statut pending), puis émis. Au redémarrage, NexusSyncService.replayPendingEvents() rejoue les entrées pending. Aucune vente ni mouvement de stock ne peut disparaître en cas de crash navigateur entre le Nexus.adapter.set() et le emit().
✓
Dead Letter Queue (DLQ) — backoff exponentiel
Si un handler throw, l'événement est capturé dans la table deadLetterEvents (status retry). Backoff : 2^attempts × 1 000 ms. Après 5 tentatives → statut quarantine. Le panneau MCC /admin/mcc/event-bus (EventBusHealthPanel) permet de relancer ou d'archiver manuellement.
✓
Payload Versioning (v: 1)
Tous les événements portent un champ v: 1 (literal type). Le PayloadMigrator permet des migrations transparentes v0 → v1 sans breaking change. La DLQ affiche la version du payload bloqué pour faciliter le debug.
✓
Bouclier IA — Backpressure IntelligenceHandler
Debounce 30s sur les appels Gemini (coalescence des order.paid en fenêtre glissante). Circuit breaker 3 erreurs → pause 60s sur GeminiProvider. Évite un DDOS interne lors des coups de feu (100 commandes/h).
📋 Checklist — Ajouter un nouvel événement (8 étapes)
  1. Déclarer l'interface dans NexusEvents (src/shared/eventBus/NexusEventBus.ts) avec v: 1 littéral et tous les champs tenantId obligatoires.
  2. Choisir la priorité : CRITICAL si fiscal/souveraineté, HIGH si stock/RH/compliance, BACKGROUND si IA/CRM/météo.
  3. Créer le handler dans src/shared/eventBus/handlers/ ou src/modules/<pilier>/handlers/.
  4. Enregistrer le handler dans registerHandlers.ts.
  5. Utiliser emitDurable() (pas emit()) si l'événement est lié à une transaction fiscale, un mouvement de stock ou une opération RH critique.
  6. Écrire au moins 1 test Vitest : happy path + handler qui throw (vérifie entrée DLQ).
  7. Vérifier npx tsc --noEmit → 0 erreur.
  8. Ajouter une ligne dans la table des événements du chapitre 26 de la Bible.
🚫 Règles Invariantes du Bus
1
emitDurable() obligatoire sur les chemins fiscaux
order.paid, waste.logged, cash_drawer.opened_unauthorized, supplier.invoice_processed : toujours emitDurable. Un emit() nu sur ces événements = bug de résilience potentiel.
2
SovereignGuard non-contournable, même dans les handlers CRITICAL
Un handler CRITICAL peut écrire dans Nexus, mais doit toujours passer par le path tenants/{tenantId}/... avec le tenantId du payload, jamais hardcodé.
3
Jamais de delete / update sur les collections fiscales depuis un handler
journalEntries, fiscalSeals, fiscalLedger sont immuables. Un handler peut en créer de nouvelles entrées via FinancialNexusBridge.processOrder(), jamais en modifier.
4
Un handler BACKGROUND ne doit jamais bloquer
Si un handler BACKGROUND throw, l'erreur est loguée mais ne doit pas être re-throw vers la DLQ (sauf configuration explicite). Les erreurs BACKGROUND sont des dégradations gracieuses, pas des incidents critiques.
5
Tout nouveau handler est couvert par un test avant merge
Happy path + cas handler-qui-throw. Le test vérifie que la DLQ a reçu l'entrée en cas d'échec répété. Sans test = code mort.
