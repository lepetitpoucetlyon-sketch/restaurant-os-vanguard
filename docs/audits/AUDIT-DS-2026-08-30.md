## Variantes couvertes vs manques identifiés

### Button — couverture complète

Le cva de `Button.tsx` couvre tous les cas identifiés dans l'audit :
- `default` : action primaire (bg-action-primary)
- `destructive` : suppression
- `outline` : action secondaire bordée
- `secondary` : action neutre
- `ghost` : action discrète (icon buttons, toggles)
- `link` : lien inline
- `success` : validation positive

Aucune variante métier custom nécessaire (POS/KDS/etc. utilisent `variant="ghost"` avec className métier).

### Input — variantes partielles

- `Input` : base (text, email, number)
- `GlassInput` : variante glassmorphisme
- `SearchInput` : avec icône loupe intégrée
- `PremiumSelect` : dropdown
- `TimePicker` : horaire
- `QuantitySelector` : incrémenteur numérique (0 usage aujourd'hui, prêt à consommer)

**Manques** : Textarea multi-ligne non primitif (utilisé raw dans quelques écrans), Combobox recherche + sélection non primitif.

### Layout — coverage

- `PageShell` : coquille standard
- `ResponsiveShell` : split responsive
- `BentoGrid` : grille asymétrique (dashboard riche)
- `StatGrid` : grille de KPIs
- `SectionCard`, `SectionHeader`, `ContentSection` : sections

Suffit pour les écrans opérationnels.

### Feedback / status

- `EmptyState`, `LoadingState`, `Feedback`, `Toast`, `StatusBadge`, `Skeleton`, `SkeletonList`
- `CelebrationParticles` (0 usage) : célébration après action réussie

## Tokens sémantiques adoptés

La mesure `adopteVraimentDs()` accepte deux voies :

**Voie 1 — Import + usage d'une primitive de `@/shared/components/*`**

**Voie 2 — Utilisation massive (≥ 5 occurrences) de tokens sémantiques** :
```
bg-surface-{card|hover|glass|primary|tertiary}
bg-action-{primary|primary-hover}
bg-status-{success|warning|danger|info}
text-brand[-*], text-text-{primary|secondary|muted}
text-status-{success|warning|danger|info}
text-on-{primary|surface}
border-border-{default|subtle}
ring-focus, ring-accent
```

**398 fichiers** (485 → 87 après voie 2) passaient sans importer de primitive UI mais utilisant les tokens = vraie adoption DS par système de design tokens.

## Marketing — exception documentée

`src/app/(marketing)/**` est exempté du cliquet DS opérationnel (décision produit 2026-08-30) : design de conversion volontairement distinct (glassmorphisme sombre, gradients aurés) pour le funnel prospects. Ce n'est pas le même produit visuel que l'UI applicative (gérant/serveur).

Si besoin de formaliser à terme, créer `src/app/(marketing)/design-tokens.ts` avec ses propres tokens documentés.

## Recommandations

### Court terme (immédiat)

1. **Adopter les primitives orphelines** dans les écrans où elles ont du sens :
   - `Chip` → remplace les badges custom (nombreux dans POS)
   - `Spinner` → remplace les loaders custom
   - `DateNavigator` → remplace les navigations de dates custom
   - `QuantitySelector` → remplace les +/- custom dans POS/inventory
   - `ToolbarTabs` → remplace les onglets custom dans dashboards
2. **Créer une primitive `Textarea`** — utilisée en raw dans plusieurs écrans (notes, commentaires, descriptions).
3. **Créer `Combobox`** (search + select) — pattern récurrent en raw.

### Moyen terme (sprint DS)

1. **Refactor 19 hors-DS opérationnels** par vagues :
   - Vague 1 : écrans applicatifs prioritaires (5 fichiers)
   - Vague 2 : composants shared (9 fichiers)
   - Vague 3 : contextes custom (5 fichiers)
2. **Formaliser la palette marketing** dans `src/app/(marketing)/design-tokens.ts` pour éviter les couleurs `white/[0.02]` hardcodées.
3. **Ajouter un lint rule** : `no-raw-button`, `no-raw-input` pour empêcher toute régression future dans le code applicatif (hors marketing).

### Long terme (stratégie DS)

1. **Storybook interne** documentant les 52 primitives + leur cvα de variantes.
2. **Story visuelle** pour chaque orpheline (Chip, Feedback, etc.) → adoption facilitée.
3. **Tokens sémantiques v2** : distinguer opérationnel / marketing / dashboard admin, chacun avec sa palette héritée.
