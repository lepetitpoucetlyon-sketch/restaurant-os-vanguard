## FAMILLE A — Sécurité & Conformité

### Axe 1 — Routes API non gardées 🔴

**Mesure**
```
210 routes (route.ts)
166 avec requireAnyAuth | adminAuthGuard | requireMccLevel | verifySignature
 44 sans guard détecté
```

**Analyse par catégorie**

| Catégorie | Routes | Verdict |
|---|---|---|
| Légitimement publiques | `health` · `status` · `menu.json` · `v1/openapi.json` · `resolve-domain` | 🟢 Normal |
| Webhooks (signature attendue) | `stripe` · `thefork` · `google-reserve` · `docuseal` · `sms/inbound` · `delivery/[provider]` | ⚠️ **Vérifier que chacun valide sa signature** |
| Widget public | `widget/book` · `widget/availability` · **`widget/setup-intent`** | 🔴 `setup-intent` crée une intention de paiement |
| Cron | `cron/daily-backup` · `cron/weekly-report` | 🔴 Déclenchables par quiconque ? |
| Métier exposé | **`haccp/iot-push`** · `promotions` | 🔴 `iot-push` écrit de la **donnée de conformité** |
| Facturation | `billing/signup` · `billing/dunning` | 🔴 Argent |

**Risque concret**
`haccp/iot-push` sans authentification permet d'injecter de fausses relevés de température.
En cas de contrôle sanitaire ou d'intoxication, le registre HACCP fait foi — un tiers pourrait
falsifier la preuve de conformité d'un restaurant, ou un restaurant pourrait nier l'avoir fait.

**Ce qu'il faut vérifier route par route :** signature, secret partagé, ou token de service.

### Axe 2 — RGPD & données de santé 🟠

**Mesure** — 48 fichiers dans `src/modules/compliance/reglementaire/` · route `admin/fleet/rgpd-export` présente.

**Le point non traité**
Un restaurant stocke : réservations nominatives, préférences, **et allergènes**.
Les allergènes sont une **donnée relative à la santé** au sens de l'article 9 du RGPD —
catégorie particulière, régime renforcé : base légale explicite, minimisation, durée de
conservation courte, journalisation des accès.

Le code manipule les allergènes à plusieurs endroits (`ALLERGENS` dans `constants/product-form`,
`selectedAllergens` dans `ProductFormModal`, règle `crm.allergen_flagged` dans le bus).

**À auditer :** durée de rétention, droit à l'effacement effectif sur les réservations,
export de portabilité complet, journal d'accès aux données d'allergènes.

## FAMILLE B — Résilience & Exploitation

### Axe 6 — Gestion d'erreur UX 🔴 *(découverte majeure)*

**Mesure**
```
find src/app -name "error.tsx" -o -name "global-error.tsx" -o -name "not-found.tsx" -o -name "loading.tsx"
→ 1 fichier au total
ErrorBoundary référencé dans 2 fichiers
```

**Ce que ça signifie concrètement**
Next.js App Router utilise `error.tsx` par segment pour capturer les erreurs de rendu.
Sans lui, une exception non gérée affiche **la page d'erreur générique de Next** — écran
blanc, message technique, aucune action possible.

**Scénario réel :** un serveur en plein coup de feu, une erreur survient sur `/pos`.
Il obtient un écran blanc. Il n'a pas de bouton « réessayer », pas de message métier,
pas de moyen de sauver sa commande en cours. Il redémarre la tablette et perd le panier.

**C'est le défaut le plus visible côté client de tout cet audit** — et l'un des moins chers
à corriger (un `error.tsx` par groupe de routes).

### Axe 7 — Impression & matériel dégradé 🔴

**Mesure** — `PrintingService.ts` contient **un seul bloc de gestion d'erreur** :
```typescript
try {
  …
} catch { /* ignore */ }
```

**Ce qui manque pour un usage réel**

| Cas | Comportement attendu | Présent ? |
|---|---|---|
| Imprimante hors ligne | File d'attente + réémission | ❌ non vérifié |
| Plus de papier | Alerte visible en caisse | ❌ |
| Ticket fiscal non imprimé | **Ne jamais perdre le ticket** (NF525) | ❌ à vérifier |
| Timeout réseau (imprimante IP) | Retry borné + repli | ❌ |
| Tiroir qui ne s'ouvre pas | Message + procédure manuelle | ❌ |

**Nuance importante :** les 6 adapters sont propres et testés unitairement
(`escpos-builder.test.ts`). Ce n'est pas la génération du ticket qui est en cause,
c'est **l'orchestration en cas d'échec**.

**Enjeu fiscal :** si un ticket est scellé mais jamais imprimé, quelle est la position
NF525 ? Le scellement fait foi, mais le client attend un justificatif. À trancher.

## FAMILLE C — Généralisation & Marché

### Axe 13 — i18n métier 🔴 *(découverte majeure)*

**Mesure**
```
'EUR' en dur     : 129 occurrences
Taux TVA en dur  : 209 occurrences
'fr-FR' en dur   : 177 occurrences
```

**Nuance importante — ce n'est pas de la négligence**
`TaxRateGuard.ts` centralise les taux et documente précisément son intention :
> Article 289 CGI + Décret NF525 : chaque ligne de vente doit porter un taux de TVA explicite.
> […] refuse la validation si UN item n'a pas de `taxRate` dans `["0.055","0.10","0.20","0.00"]`
> (taux ORTA France 2026).

C'est un **choix de conformité délibéré et bien argumenté**, pas du code sale.

**Mais la conséquence stratégique est majeure**
Le produit est **verrouillé sur la France et l'euro**. Vendre en Belgique (TVA 6/12/21 %),
en Suisse (CHF, 2,6/8,1 %) ou au Luxembourg demanderait de rendre `TaxRateGuard`
configurable par tenant, plus 129 points de devise et 177 de locale.

**C'est un axe qui dépasse de loin l'i18n de chaînes déjà audité.**
Traduire l'interface en anglais ne sert à rien si la caisse ne sait facturer qu'en TVA française.

**Décision à prendre :** France-only assumé (et documenté), ou ouverture multi-pays planifiée.

## 🔴 SPRINT A — Avant le premier client *(3-4 sessions)*

### A.1 — Pages d'erreur Next.js · *1 session*
**Pourquoi en premier :** défaut le plus visible, correction la moins chère.

Créer :
```
src/app/global-error.tsx                    → filet global
src/app/(client)/(ops)/error.tsx            → erreur métier avec « Réessayer »
src/app/(client)/(ops)/pos/error.tsx        → spécifique POS : préserver le panier
src/app/(admin)/error.tsx
src/app/not-found.tsx
```
Le `error.tsx` du POS doit **sauvegarder le panier dans l'atome avant d'afficher l'erreur**,
et proposer « Reprendre la commande ».

*Critère :* provoquer une erreur sur `/pos` → écran métier, panier récupérable.

### A.2 — Sécuriser les routes API sensibles · *1 session*
Traiter dans l'ordre :
1. `haccp/iot-push` → token de service par device (donnée de conformité)
2. `cron/*` → secret de cron partagé
3. `widget/setup-intent` → limitation de débit + validation d'origine
4. Vérifier la signature de chacun des 6 webhooks

*Critère :* un test qui échoue si une route hors liste blanche n'a aucun garde.

### A.3 — Résilience d'impression · *1 session*
File d'attente d'impression persistée + retry borné + alerte visible en caisse.
Trancher explicitement le cas « ticket scellé, impression échouée ».

*Critère :* débrancher l'imprimante en plein service → le ticket part en file, l'opérateur est prévenu, rien n'est perdu.

### A.4 — Instrumenter Sentry · *0,5 session*
Brancher `sentry.ts` sur les `error.tsx` créés en A.1 + les routes API critiques.

*Critère :* une erreur provoquée apparaît dans Sentry avec tenant et route.
